## DLL workflow

C1 and C1XX export `_InvokeCompilerPass@12` and `_AbortCompilerPass@4`, by
ordinals 2 and 1 respectively. The invoke arguments are `argc`, `argv` and a
Boolean derived from CL's pass flags. The third argument is not a callback table.
RCDLL exports `RC` and `Handler`; RC.EXE supplies a diagnostic callback to `RC`.
See each binary's investigation for the actual calling conventions and callsites.

The preferred initial native target compiles each reconstructed DLL's C sources
into a separate i386 test harness. That harness supplies the captured host
contract and faithfully invokes attach, exported entry and detach paths. Harness
functions stay outside the target graph and trace. The original-toolchain target
remains a real Win32 DLL with its original export names, ordinals and signatures.
This avoids requiring ELF shared-object tracing for the initial cases.

DLL initialization is part of the target. Identify traps by target hash and RVA,
retaining the actual loaded base separately. Stop on DLL load and guard its CRT
entry before continuing; stopping at the driver's main entry is too late for
statically imported DLLs. All three current DLLs have no TLS directory. For these
targets, a verified non-relocated entry byte can first receive a breakpoint;
the first entry trap then provides a point to mask instructions after loader
relocation but before target code executes. Verify this staging in the eventual
masked runner, including a nonpreferred-base case. Snapshot the relocated loaded
bytes there and restore accepted ranges from that snapshot, rather than raw
on-disk bytes. Record preferred and actual bases with RVA projections. This
staging also requires verifying that no import cycle calls the target before its
entry guard. Preserve DLL CRT
initialization, application DllMain, per-invocation initialization and cleanup as
distinct paths. A future DLL with TLS callbacks needs earlier callback guards.

Executable sections can also contain loader data: CVTRES has its IAT, import
tables and debug metadata inside `.text`. Preserve proven loader metadata and
data ranges when masking; do not equate an executable section with code bytes.

Target HMODULEs and resource identities must describe the original DLL, rather
than the native harness. Resource strings, resource lookup and module filename
behavior need explicit captured metadata and shared support where encountered.
Do not replace imported MSVCRT, MSPDB50 or MSDIS100 contracts with guessed Win32
shims. Inventory actual use and agree on dependency boundaries before adding
support or claiming case readiness.

Concrete module-resource requirements found so far are C1/C1XX `LoadStringA`
using the HINSTANCE cached by DllMain, and RCDLL `FormatMessageA` with
`FROM_HMODULE | IGNORE_INSERTS` against its embedded message table. The shared
library currently has no target-module resource registry. These are readiness
requirements, not implemented shims.

## Builds and references

Use the shared repo Wine prefix and fixed R:/S: drives described in root
AGENTS.md. Keep scratch under `~/.ai-tmp/msvc2/vc5.10/<binary>/<case>`.
Wine is used only for explicit original builds and reference investigations;
native fixtures never invoke it. Existing per-binary Makefiles expose groundwork
commands and refuse reconstruction builds until their prerequisites exist.
Native DLL harnesses, debugging and dependency handling remain entirely Linux
native. Do not run PE or Wine helpers for DLL, PDB or other dependencies; use
strict previously captured responses or an evidenced native implementation.

The experimental Rust graph auditor currently understands PE32 bytes, including
DLLs, but its verified profiles cover vc1.0. VC 5.10 profiles must describe the
actual graph roots, import/runtime boundaries, export aliases and any executable
text data. Keep module identities distinct if a later case needs multiple
reconstructed modules in one run. Do not integrate the new auditor during this
groundwork phase.

The shared auditor can provisionally read a DLL using the CL-shaped index format
and explicit original/rebuilt/MAP/config/runtime paths; that format has no fixed
CL addresses. Function names must match decorated MAP symbols. Supply explicit
entry roots, text data and switch targets. Export ordinals/signatures, DLL loader
contracts and the native harness require separate checks; PE graph support alone
does not certify them. Review this metadata policy before integration.
