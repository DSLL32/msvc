Independent C1/C2/LINK cases captured from vc1.0 CL

Source: int main () { return 0; }
Original invocation: toolchains/1.0-nt/bin/CL.EXE test.c
No diagnostic switches were passed to CL or its compiler phases.

manifest.json contains each target hash, the captured application/command line,
exact MSC_CMD_FLAGS value, portable environment template, and file hashes.
C1 and C2 receive no command-line options. CL supplies a one-entry environment
block containing only MSC_CMD_FLAGS. Both phases inherit CL's working directory
and standard handles. The captured case has closed stdin and empty phase stdout
and stderr; each phase returns 0.

The portable templates replace the original temporary basename with relative
"ir" and the original toolchain paths with {bin}/{include}. Preserve all other
characters, including the final space. Substitutions are Windows paths. The
independent original-toolchain checks confirm these replacements preserve C1's
outputs exactly and C2's object except its COFF timestamp.

C1 case:
 - Copy c1/test.c to an isolated working directory.
 - Set the environment using phases.c1.environment and launch C13232.EXE.
 - Compare generated irex, irsy, irin, irgl against the files under c2/.

C2 case:
 - Copy c2/irex, irsy, irin, irgl to an isolated working directory.
 - Set the environment using phases.c2.environment and launch C23232.EXE.
 - Compare generated test.obj against expected/test.obj, ignoring only bytes
   4..7 (the four-byte COFF TimeDateStamp).
 - No test.c, frontend process, or linker process is required for this case.

LINK case (queued after the LINK reconstruction's initial /? case):
 - Copy link/test.obj and link/link.rsp to an isolated working directory.
 - Set LIB to the original toolchain's lib directory; clear LINK and _LINK_.
 - Launch LINK.EXE with command-line arguments: -link @link.rsp
 - LINK inherits the environment; CL passes a null environment pointer rather
   than the compiler phases' single-entry MSC_CMD_FLAGS environment block.
 - The response file contains exactly these three lines, with CRLF endings:
       -out:test.exe
       -debug:none
       test.obj
 - The object selects the original LIBC.LIB; its hash is in the manifest.
 - Compare test.exe against expected/test.exe, ignoring only the four-byte
   PE COFF TimeDateStamp at offset 0x88. The generated program must return 0
   without output. No compiler process is required for this case.

The four intermediate files are 866, 13, 3, and 50 bytes, respectively. They are
unmodified files generated by original C1, captured immediately before original
C2 was launched. They are test inputs, not snapshots of executable sections.
Their internal formats have not been decoded.

Verify all three cases from any working directory:

    python3 /root/msvc2/decomp/vc1.0/fixtures/minimal-c/verify.py

Select one with a c1, c2, or link argument. The verifier builds run-phase.c using the
original compiler/linker, creates a private 32-bit prefix, and uses isolated
working directories under ~/.ai-tmp/vc1.0-capture/. The launcher explicitly
passes the single-variable environment block for C1/C2 and inherits the
environment for LINK, reproducing CL's launch policy for each process.

Capture provenance:

capture-cl.c is the debugger used to observe unmodified original CL. At CL's
CreateProcessA import thunk (original VA 0x21000, RVA 0x11000), it reads the real
Win32 API arguments, records application/command/environment/current-directory
parameters, then resumes CL. Before the second launch it copies the four
intermediate files while C2 has not started. Before the third launch it copies
the response file and object while LINK has not started, and records inherited
LIB. The original CL subsequently
finishes compiling and linking normally, with exit 0.

Compile capture-cl.c with the original toolchain as a console program. Its four
arguments are the original CL Windows path, thunk RVA "11000", output directory
Windows path, and working directory Windows path. Both directories must exist;
the working directory must contain test.c. Run with closed stdin. Captures and
scratch builds belong under ~/.ai-tmp. No original executable on disk is changed.
The debugger restores its one-byte observation breakpoint before executing the
original import thunk, then reinserts it for the next launch.
